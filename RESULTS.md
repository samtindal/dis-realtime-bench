## How it was measured

- **Two kernels.** ESPDU decode: 144-byte Entity State PDU, about 40 bounds-checked big-endian
  field reads, zero allocation. DRM_RVB dead reckoning: body-frame rotation with 6 trig calls,
  3×3 matrix construction and three mat-vec products per entity.
- **Corpus.** 1,024 PDUs (147,456 B), sized to stay in L1/L2 so the codec is measured, not
  memory bandwidth. Identical bytes in every language, checked by FNV-1a hash.
- **Unit of measurement.** One call. The decoder and the DR function are marked never-inline in
  every language, so each timed loop calls the same out-of-line function (see README, trap 4).
- **Dependency-free harness** in each language: at least 5 batches and at least 1,000 ms of warmup,
  then 200 timed batches of 1,024 operations per run. Ten rounds; each round runs every binary once
  in a fixed order, so drift hits all of them equally. Median and interquartile range, never the mean.
- **Ecosystem harnesses:** Google Benchmark 1.9.5 (20 repetitions), Criterion 0.8.2 (100 samples),
  BenchmarkDotNet 0.15.8 (default job, `[MemoryDiagnoser]`).
- **Equivalence gate.** Before any timing, every binary dumps every decoded field and every DR
  output as IEEE-754 bit patterns; `scripts/verify.py` requires all dumps to be byte-identical.
- **cycles/op** uses the clock measured by `bench calibrate`, a dependent chain of 1-cycle adds.

Clock for cycles/op: 4.020 GHz (scripts: bench calibrate).

## Mechanisms (verified in disassembly or by microbenchmark)

Instruction statistics for the exact functions the timed loops call:

| clang | `decode_espdu<LoadShift>` | 305 | 46 | 19 | 66 | 59 | 0 | 0 | Reader<LoadShift>::f64×3 |

| rust | `decode_espdu [543661]` | 246 | 37 | 22 | 31 | 63 | 0 | 0 | — |
| rust | `decode_espdu [7bf7ac]` | 246 | 37 | 22 | 31 | 63 | 0 | 0 | — |

**GCC dead reckoning is ~1.9× slower than clang: half explained.** Clang and rustc merge each
`sin`/`cos` pair into Apple's `__sincos_stret`. GCC performs the same merge but lowers it to
`cexp(i·x)` (4 calls), because it does not know Darwin's `__sincos_stret`. A microbenchmark of
the two libm entry points on the same inputs:

| call | ns per call |
|---|---:|
| `__sincos_stret` | 3.45 |
| `cexp(i·x)` | 6.59 |
| `sin` + `cos`, separate calls | 2.76 |

Four `cexp` calls cost ~12.6 ns more per entity than four `__sincos_stret` calls. That is about
half of GCC's ~25 ns deficit. **The other half is not explained.**

**Clang's shift-loop decode is ~1.5× slower than its bswap decode.** Clang does not combine the
8-iteration byte loop in `LoadShift::u64` into one load and byte swap: 66 loads versus 38, and it
calls `Reader<LoadShift>::f64` out of line three times. GCC mostly combines it (13 byte-swaps
and 27 loads, versus 14 and 20 in its bswap version), and pays 1.08× rather than 1.47×.

**Rust's two idioms compile to identical machine code.** Both `decode_espdu` instances are
246 instructions with the same statistics. LLVM recognises Rust's shift loop over a `[u8; 8]`,
which is why `idiomatic` and `shift` time the same.

**Rust decode is ~1.19× slower than C++.** The Rust decoder performs 63 stores versus 36 in
clang's. That is consistent with building `Option<EntityState>` and copying it to the return
slot, where C++ writes through an out-parameter. This is *consistent with* the data, not proven.

**GCC's timed loop calls the full, bounds-checked decoder.** GCC also emits a `.constprop`
clone with the length folded to 144 (1 conditional branch). Only the `dump` path uses it; the
timed loop calls the 27-branch checked version, through a Mach-O stub.

**C# JIT versus NativeAOT.** Dynamic PGO explains most of the decode gap: with
`DOTNET_TieredPGO=0` the JIT's idiomatic decode goes from 21.2 to 23.7 ns, against NativeAOT's
25.5 ns. It explains none of the DR gap (JIT 49.0 ns, NativeAOT 58.6 ns). Both runtimes call
`Math.Sin` and `Math.Cos` separately (4 + 4 calls, seen in `DOTNET_JitDisasm` and in the AOT
binary's imports), but separate calls are *faster* than the merged call (table above), so that
does not explain C#'s DR cost either. **Not explained.**

## Two harnesses per language agree

Every ecosystem harness lands within 0.96–1.10× of the dependency-free harness for the same
implementation (table above). Agreement is weak evidence that neither harness is lying. Before
the inlining boundary was fixed, the same comparison disagreed by 2× (README, trap 4).

## Observed but unexplained: bimodal timings

During development, the Rust DR benchmark produced two stable modes, ~28 ns and ~35 ns, with
machine code identical between harnesses. Each mode persisted for 0.5–10 ms. Ruled out: code and
loop alignment (64-byte alignment changed nothing), the calling frame, output syscalls between
batches, and CPU frequency (a 30 µs-window clock probe showed no plateau near the 3.3 GHz the
ratio implies). The committed full run did not reproduce it (IQR 27.9–28.2 ns). Mitigation:
200 batches per run and 10 interleaved rounds, so a run spans many such windows and the IQR
exposes a second mode if one appears.

## What was not measured

x86 (the preliminary handoff numbers were from an x86 VM and are not comparable), multiple
machines, AC power, allocation-heavy workloads, multi-threaded scaling, startup time, compile
time, binary size, and inlined-loop performance (the never-inline boundary is a choice; see README).
